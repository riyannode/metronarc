Use the host's intelligence and existing connected apps. METRON owns deterministic economic policy, local SQLite state, payment evidence, and accounting. Email belongs to the host.

Run `python3 -B <plugin-root>/skills/metron/scripts/run.py --help` to inspect available operations. `status` safely initializes the local SQLite ledger on first use and reports an empty ledger; run it even when `~/.metron/metron.sqlite` does not exist yet. Send structured mutation input through a JSON file using `--input`; never interpolate user text into shell commands.

### Dashboard

When the user naturally asks to open or show the METRON dashboard, or view METRON operations, invoke the existing `dashboard` operation. The user does not need to know or type the Python command. Do not open the dashboard automatically when the plugin is installed or initialized.

`dashboard` regenerates `~/.metron/dashboard.html` from the canonical local `~/.metron/metron.sqlite` state and opens it in the local default browser. `dashboard --no-open` regenerates the file without opening a browser. The HTML is a static local snapshot, not a live hosted UI: it does not poll Circle or show a live Circle wallet balance. Circle and other external activity appears only after authoritative METRON reconciliation has persisted it to SQLite.

After a business-state command returns successfully, following its persistence logic (goal creation; spend proposal, approval, execution, or reconciliation; deal mutation; or invoice mutation), the runtime silently regenerates the snapshot if `~/.metron/dashboard.html` already exists. This refresh does not open a browser or make Circle reads. Commands that fail with an error do not enter this path. If an authoritative operation successfully persists a `FAILED` or `UNKNOWN` result, the refreshed dashboard retains that exact status; generation never upgrades it to success.

Rules:

1. Create and evaluate a Spend Intent before every paid economic action. Search, inspect, or estimate a Circle service before proposing payment. Copy the inspected HTTP method, `exact` or `GatewayWalletBatched` payment scheme, accepted Arc Testnet chain, and seller wallet into `http_method`, `payment_scheme`, `accepted_chains`, and `payee_address`; include the exact request body in the proposal. Immediately before dispatch, METRON re-estimates and requires the same scheme, seller, and chain within the approved maximum. `exact` checks on-chain wallet USDC; `GatewayWalletBatched` checks the chain-scoped Circle Gateway available balance. There is no fallback between these pools, and each must cover `approved_max_cost + minimum_wallet_balance`.
2. Execute only an intent in `APPROVED` state. `ALLOW` intents become `APPROVED` automatically; `ESCALATE` intents require an explicit persisted `spend-approve` decision first. `DENY` is terminal and cannot be human-overridden. The request body at execution must match the proposal hash. METRON checks Circle payment metadata and authoritative transaction history against the approved seller, wallet, chain, amount, and maximum. Do not retry an ambiguous payment; preserve `UNKNOWN` and reconcile using authoritative Circle state. If the CLI response omitted its transaction hash, use `payment-reconcile --id SI-... --provider-ref <Circle transaction ID or hash>`.
3. `payment_evidence.tx_hash`, when present in authoritative Circle/Arc settlement evidence, is the actual Arc transaction hash and explorer-verifiable settlement reference. Keep a provider or Gateway transfer ID in `provider_ref`; do not fabricate a transaction hash or explorer link when only that ID is available. `revenueEvidenceHash` is an active domain-separated METRON provenance commitment, never an Arc transaction hash and never a replacement for `tx_hash`. A transaction hash or provider response is evidence, not the business transaction. Only METRON's Payment Entry and balanced Journal Entry record the economic result.
4. Escalate custom or legal commercial terms for explicit persisted human review by setting `custom_or_legal_terms: true` when creating a deal. Any non-payer-wallet field in the deal `terms` object also triggers this gate. Terms below the goal's `minimum_deal` require a separately persisted `deal-approve` exception while the deal is `NEGOTIATING`; these pre-acceptance approvals do not advance the deal or replace the final approval after customer acceptance. Only call `deal-accept` from `NEGOTIATING`. When a customer explicitly accepts terms, persist `PENDING_HUMAN` and ask the human. Do not invoice until that separate final approval is recorded. Generic `deal-update` cannot bypass either gate.
5. Never create journal lines directly. Never mark an invoice paid from a customer's claim, screenshot, pasted hash, or submission response.
6. At human deal approval, persist the customer's agreed `payer_wallet` (either in deal terms or approval input). Reconcile only confirmed incoming USDC matching the invoice amount, payer wallet, operating-wallet destination, configured chain, open status, and unused evidence.
7. Continue from `~/.metron/metron.sqlite` across host sessions. Never delete local state to escape an unknown payment outcome.
8. In WSL, use METRON's Circle wrapper for Circle calls so the installed Windows Node runtime and Circle CLI home stay consistent; do not invoke the WSL `circle` shell launcher directly. Never expose Circle session data or request a private key. OTP entry is handled by Circle CLI and is not stored by METRON.
9. Before the first Circle CLI action on a host, check `circle-terms-status`. If Circle reports the current Terms are unaccepted, show the returned Terms of Use and Privacy Policy URLs and ask the user to explicitly accept them. Only after a clear affirmative response, call `circle-terms-accept` with `{"confirmed":true}`. Never infer consent from installing or using METRON, and never bypass the gate with `CIRCLE_ACCEPT_TERMS`.
10. Use the host's connected email capability for customer communications. Stop outreach when asked to unsubscribe or stop.
11. Treat testnet evidence as testnet and never claim mainnet settlement or production readiness from it.
12. The Circle Agent Wallet is the only operating-money account and pays x402 services directly. Never create or use a custody vault or intermediate balance. `EconomicRegistry` is active shared provenance infrastructure on ARC-TESTNET at `0xf91f72c2eef95f936d1a8a3dfbe3cb05a92c9e38`; users do not deploy or fund it. METRON submits only `recordSpend` and `recordRevenue` after local Circle reconciliation and journal posting. SQLite and the journal remain business truth; registry failure never reverses them or changes Circle settlement to `UNKNOWN`. Revenue recording requires an explicit `originating_spend_intent_id` on the deal, same-goal validation, and confirmed spend evidence. Revenue evidence hashes bind only external settlement fields and exclude local IDs. Use `registry-sync` to read back pending/unknown records before any retry; never issue generic contract calls or treat provider references as Arc transaction hashes.

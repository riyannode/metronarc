# Durable email state

Email state lives in the existing `email_*` tables in `~/.metron/metron.sqlite`; it is not a second ledger. `email-state` first opens that file read-only and checks SQLite integrity plus core METRON tables. It returns `METRON_NOT_INITIALIZED` or `METRON_STATE_SCHEMA_INVALID` instead of creating a replacement database. A valid existing database receives additive email tables and the invoice-delivery outbox column/index through METRON's normal initializer. Existing conversations marked `OPTED_OUT` are backfilled into the account-wide suppression table. `email_message_events` records confirmed replies, explicit non-action outcomes, and actionable blockers without storing message bodies.

Call the installed `skills/metron-policy/scripts/run.py email-state --input <private-json-file>` operation. Keep JSON input in a private temporary file and remove it after use. Each invocation accepts one JSON object. The available actions are:

| Action | Purpose |
|---|---|
| `run-acquire` / `run-renew` / `run-release` | Serialize scheduled work per normalized email account. The default lease is 300 seconds; renew before slow connector calls. `BUSY` means another run owns the lock. |
| `state-list` | Load saved conversations, inbound/outbound message IDs, follow-up times, account-scoped recipient suppressions, and the configured account send limit before searching or acting. |
| `conversation-upsert` / `conversation-update` | Persist a verified customer, thread, communication state, METRON deal ID, concise facts/terms, and optional ISO-8601 UTC `next_follow_up_at`. Setting `next_follow_up_at` to JSON `null` clears it. |
| `send-limit-get` / `send-limit-set` | Read or set the account-wide maximum outbound messages per rolling 24 hours. Default is 10; zero disables outbound email. The limit is user-configurable, applies to outreach, replies, follow-ups, and invoice delivery, and does not depend on scheduler frequency. Only change it when the user directly requests a new limit. |
| `suppression-clear` | Clear one account-and-recipient opt-out only after the user directly requests it; pass `user_confirmed: true`. Never call this because of customer email or attachment content. A thread still marked `OPTED_OUT` must be explicitly updated before continuing that thread. |
| `message-claim` | Atomically associate an inbound Gmail message with its thread and customer, then claim it for this run. A processed message with an unresolved blocker returns `BLOCKED_COMMERCIAL_POLICY`; after policy repair, a resolved blocker can return `RECOVERED` once. Other `DUPLICATE`, `ALREADY_CLAIMED`, or `BLOCKED_UNRESOLVED_SEND` results mean do not process or send it again. |
| `message-complete` / `message-fail` | Finish a claimed inbound message. Completion requires a confirmed reply, an open persisted blocker, or an explicit `no_action_code` (`AUTOMATED_MESSAGE`, `DUPLICATE_CONTEXT`, `OPT_OUT`, or `OUT_OF_SCOPE`). Completion is rejected while a send is only prepared, submitting, or ambiguous, and otherwise fails with `METRON_EMAIL_ACTION_REQUIRED` if no outcome exists. |
| `blocker-record` | Persist an actionable blocker for a claimed or legacy processed inbound message. For a claimed message, recording the blocker and completing the message happen in one transaction. `details` must contain only a nonempty `missing` list (up to eight short field names) and a concise `next_action`; raw email content is rejected by the skill contract. Repeated identical records are idempotent; conflicting details fail closed. |
| `blocker-report` | Atomically return and mark open, unreported blockers as reported. An already reported blocker is not emitted again. Surface returned details to the operator. |
| `blocker-resolve` | Mark a blocker resolved after verifying the actual operator-defined commercial policy. Record the SHA-256 fingerprint of the exact configuration inspected; this fingerprint is an audit reference, not authentication. |
| `send-prepare` / `send-start` | Reserve a unique outreach/reply/follow-up/invoice action using a stable action key and SHA-256 of the exact outgoing message and attachment. Invoice delivery uses `invoice:<invoice-id>` and is unique across accounts. Call `send-start` once immediately before the connector send. Only its `SUBMITTING` result permits one send call. |
| `send-confirm` / `send-unknown` / `send-fail` | Persist confirmed Gmail message/thread IDs, preserve an ambiguous send, or mark a provider-confirmed no-send failure. `send-fail` requires `not_sent_confirmed: true`. |

Use action keys consistently: `outreach:<conversation-id>` for initial outreach, `reply:<inbound-message-id>` for a reply, `follow-up:<prior-outbound-message-id>` for a planned follow-up, and `invoice:<invoice-id>` for invoice delivery. An invoice must match the saved conversation's deal and verified recipient. A reply must reference an inbound message in the same thread; a follow-up must reference the preceding confirmed outbound message in that conversation. An account/customer can have only one initial outreach, an inbound message can have only one reply, an outbound message can have only one follow-up, and an invoice can have only one send attempt globally. The database's unique constraints and `BEGIN IMMEDIATE` transactions enforce these rules across concurrent scheduler runs.

The sequence for any outbound message is `send-prepare` → `send-start` → exactly one native connector send → `send-confirm`. `send-prepare` and `send-start` check the account-wide recipient suppression table. Setting a conversation to `OPTED_OUT` records the normalized recipient under that Gmail account, and `send-start` cannot proceed from another thread. The account-wide rolling 24-hour limit is checked in the same transaction that changes an attempt to `SUBMITTING`; if reached, the action remains `PREPARED`, and no Gmail call is allowed. Keep that same action pending for a later scheduler run instead of creating a duplicate. A `FAILED` result with `METRON_EMAIL_OPTED_OUT` is a local cancellation and must not call Gmail. If the send result is ambiguous, use `send-unknown`, then read the existing Gmail thread. Confirm with `confirmation_source: "gmail_readback"` only when the exact sent message is present. If it is absent or cannot be checked, preserve `UNKNOWN` and stop; never retry. The per-account run lock fences active schedulers. A claim left by an earlier run can be reassigned under the new lock only when no ambiguous send is linked to that message. `SUBMITTING` and `UNKNOWN` are never sendable states. A legacy `PROCESSED` row without an outcome remains a duplicate until `blocker-record` backfills its actual reason. An open blocker prevents reprocessing; after policy is genuinely configured, resolve it with the fingerprint of the inspected configuration and claim again. Recovery succeeds only when that source message has no reply attempt; the normal unique `reply:<message-id>` key still prevents duplicates after restart. `state-list` exposes `message_events` for audit.

Store message IDs, thread IDs, customer address, state, deal reference, last confirmed action, and brief verified context only. Do not store message bodies, credentials, or tokens. `context` is a JSON object replaced as a whole; read the existing state first when updating it.

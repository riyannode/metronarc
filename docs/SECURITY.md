# Security boundaries

## Privacy and data flows

METRON runs locally and has no hosted backend or separate analytics service. It stores goals, policies, counterparties, deal terms, invoices, payment references, evidence summaries, journal entries, and events in SQLite under `~/.metron/`. Local configuration and the generated dashboard are stored there too. METRON does not encrypt these files; protect them with operating-system account and device controls.

The AI host receives the prompts and context the user provides, subject to that host's own data practices. Circle CLI sends wallet and transaction requests to Circle. For an approved paid-service call, the request body and payment details are sent through Circle CLI to Circle and the selected service provider. Do not include customer data the provider does not need. Circle CLI may retain failed x402 request details in its own `~/.circle-cli/payments/` directory; that storage is outside METRON's control. METRON does not implement email delivery or send customer outreach.

- **AI host:** supplies model output and tools. A skill is guidance, not a cryptographic sandbox against a malicious host.
- **METRON local core:** makes deterministic policy decisions and writes the local ledger. A local-machine compromise can change its state.
- **SQLite:** stores goals, policies, documents, evidence references, and accounting. Keep `~/.metron/` private and backed up by the owner.
- **Circle CLI session:** holds Circle authentication outside this repository. METRON never reads or stores OTPs, session tokens, mnemonics, or private keys.
- **Circle CLI failure logs:** Circle stores failed x402 request details under its own `~/.circle-cli/payments/` directory. Do not put secrets or unnecessary customer data in a service request body.
- **Circle Agent Wallet:** holds the operating money, owns the payment signing authority, and pays x402 services directly. METRON can submit only the two bounded registry methods after reconciliation; this does not make the registry a payment authority. Testnet wallet limits are not assumed to exist; Circle documents configurable wallet limits as mainnet-only.
- **Wallet balance check:** immediately before dispatch, `exact` reads on-chain wallet USDC and `GatewayWalletBatched` reads chain-scoped Gateway available USDC. Each pool must cover the approved maximum plus the configured minimum; METRON does not fall back between them. Another wallet action outside METRON can race after that read; METRON policy does not cryptographically restrict independent Circle wallet use.
- **Circle x402 service:** may return service data and payment evidence. The provider response alone does not prove a business outcome.
- **x402 rail selection:** Circle CLI can select `GatewayWalletBatched`. METRON binds the scheme selected by its no-payment estimate and rejects a mismatch after dispatch; if a payment was submitted under a changed scheme, it preserves the result as `UNKNOWN`. Gateway transfer IDs are queried against Circle's authoritative x402 transfer API and are not treated as settled until the record matches the approved sender (Circle-resolved backing EOA), seller, sending and recipient networks, USDC amount, UUID, and terminal status. The batch transaction sender is not used as payer identity.
- **Gateway HTTP transport:** the WSL `urllib` client remains the default. `METRON_GATEWAY_STATUS_CURL_EXE` explicitly selects a native curl executable when the operator wants the Windows network stack; METRON does not automatically switch clients after a 403, change proxy settings, follow redirects, or disable TLS verification.
- **Arc settlement:** confirms chain movement; it does not prove that an invoice, customer, payee, or commercial claim is genuine.
- **METRON local core:** controls whether its own execution path permits an action, stores deterministic economic policy and canonical business records, reconciles Circle evidence, and derives any registry commitments. It cannot prevent the wallet owner from using Circle outside METRON.
- **EconomicRegistry:** active on Arc Testnet at `0x547552585d8d995c5063820b2950e0db52b4cab4` (chain ID `5042002`). It records immutable commitments after METRON reconciliation and supports multiple distinct revenue settlements per spend. It has no owner, payable entry point, token-transfer or payment method, or custody path. Unsolicited ERC-20 or forced native transfers may leave unrecoverable assets. It is not a wallet or accounting authority.
- **Settlement hashes:** `payment_evidence.tx_hash` is the actual Arc transaction hash from authoritative Circle/Arc settlement evidence when available and remains the explorer-verifiable settlement reference. A Circle provider/transfer ID is retained as `provider_ref` and is not a substitute transaction hash. `revenueEvidenceHash` is the active domain-separated METRON provenance commitment; it is not an Arc transaction hash and never replaces `tx_hash`.

## Economic and commercial approval boundaries

- `ALLOW` Spend Intents become `APPROVED` automatically. `ESCALATE` Spend Intents require explicit persisted human approval. `DENY` is terminal. Human approval of an escalated intent rechecks and cannot bypass the absolute daily-spend or available-operating-capital caps; both caps are also rechecked atomically before dispatch reservation to stop a stale approval exceeding the current day's limit.
- Expected value is not required to authorize an x402 spend. Exceeding `max_spend_per_action` escalates; exceeding `max_daily_spend` or seed budget plus earned operating capital denies. Before dispatch, the re-estimated approved maximum plus `minimum_wallet_balance` must fit in the live Circle wallet balance; failure denies dispatch.
- Realized ROI is a post-outcome metric from confirmed outgoing x402 Payment Entries for the goal and reconciled incoming customer Payment Entries for PAID invoices belonging to the goal: `(reconciled collected revenue - confirmed spend) / confirmed spend`. It is undefined when confirmed spend is zero; expected value, quoted deal amounts, open invoices, customer promises, unconfirmed payments, and registry state are excluded.
- Deals below `minimum_deal`, deals marked `custom_or_legal_terms: true`, and deals with non-payer-wallet `terms` fields require persisted pre-acceptance human approval. Customer acceptance always enters `PENDING_HUMAN` and requires a separate final decision before invoice creation. `deal-update` cannot set either approval state.
- EconomicRegistry is shared project provenance infrastructure; users do not deploy or fund it. Writes are restricted to `recordSpend` and `recordRevenue` after authoritative Circle reconciliation and local journal posting. One spend can link multiple unique revenue settlements. Registry failure never rolls back local business truth or changes Circle settlement status.
- Registry state uses a durable SQLite outbox and readback reconciliation. Ambiguous writes remain `UNKNOWN`; matching on-chain records become `CONFIRMED`; mismatches fail closed. Revenue evidence uses `METRON_REVENUE_EVIDENCE_V1`, binds stable Circle settlement fields, and excludes local business identifiers. A provider ID alone is never rendered as an Arc explorer transaction link.

Bind evidence to its source document and expected counterparty. Consume each provider reference once. If dispatch outcome is ambiguous, preserve `UNKNOWN`, query authoritative state, and do not blindly retry. Never include wallet credentials, Circle session files, OTPs, private keys, runtime SQLite, or real customer private data in the repository.

# Security boundaries

## Privacy and data flows

METRON runs locally and has no hosted backend or separate analytics service. It stores goals, policies, counterparties, deal terms, invoices, payment references, evidence summaries, journal entries, and events in SQLite under `~/.metron/`. For email-bound deals, payment-terms evidence includes a short buyer-confirmation excerpt containing the payer wallet and invoice due date, its SHA-256 digest, and source message/thread identifiers. Local configuration and the generated dashboard are stored there too. METRON does not encrypt these files; protect them with operating-system account and device controls.

The AI host receives the prompts and context the user provides, subject to that host's own data practices. The `metron-email` skill calls the host's connected email provider to search, read, send, and reply; METRON does not implement an email transport, OAuth flow, or SMTP backend. Customer message contents are sent to that provider under its own data practices. Circle CLI sends wallet and transaction requests to Circle. For an approved paid-service call, the request body and payment details are sent through Circle CLI to Circle and the selected service provider. Do not include customer data the provider does not need. Circle CLI may retain failed x402 request details in its own `~/.circle-cli/payments/` directory; that storage is outside METRON's control.

- **AI host:** supplies model output and tools. A skill is guidance, not a cryptographic sandbox against a malicious host.
- **Email connector:** sends only after the durable local action is marked `SUBMITTING`; uncertain outcomes become `UNKNOWN` and are checked in the existing thread before any further action. Customer deliverables use their own deal-bound action and require a matching closed-won email deal and confirmed source message. SQLite locks and unique action IDs reduce duplicate sends across concurrent runs, but do not constrain use of the email account outside METRON.
- **METRON local core:** makes deterministic policy decisions and writes the local ledger. A local-machine compromise can change its state.
- **SQLite:** stores goals, policies, documents, evidence references, and accounting. Keep `~/.metron/` private and backed up by the owner.
- **Circle CLI session:** holds Circle authentication outside this repository. METRON never reads or stores OTPs, session tokens, mnemonics, or private keys.
- **Circle CLI failure logs:** Circle stores failed x402 request details under its own `~/.circle-cli/payments/` directory. Do not put secrets or unnecessary customer data in a service request body.
- **Circle Agent Wallet:** holds the operating money, owns the payment signing authority, and pays x402 services directly. METRON can submit only the two bounded registry methods after reconciliation; this does not make the registry a payment authority. Testnet wallet limits are not assumed to exist; Circle documents configurable wallet limits as mainnet-only.
- **Wallet balance check:** immediately before dispatch, `exact` reads on-chain wallet USDC and `GatewayWalletBatched` reads chain-scoped Gateway available USDC. Each pool must cover the approved maximum plus the configured minimum; METRON does not fall back between them. Another wallet action outside METRON can race after that read; METRON policy does not cryptographically restrict independent Circle wallet use.
- **Circle x402 service:** may return service data and payment evidence. The provider response alone does not prove a business outcome.
- **x402 rail selection:** Circle CLI can select `GatewayWalletBatched`. METRON binds the scheme selected by its no-payment estimate and rejects a mismatch after dispatch; if a payment was submitted under a changed scheme, it preserves the result as `UNKNOWN`. Gateway transfer IDs are queried against Circle's authoritative x402 transfer API and are not treated as settled until the record matches the approved sender (Circle-resolved backing EOA), seller, sending and recipient networks, USDC amount, UUID, and terminal status. The batch transaction sender is not used as payer identity.
- **Gateway HTTP transport:** the WSL `urllib` client remains the default. `METRON_GATEWAY_STATUS_CURL_EXE` explicitly selects a native curl executable when the operator wants the Windows network stack; METRON does not automatically switch clients after a 403, change proxy settings, follow redirects, or disable TLS verification.
- **Arc settlement:** for Circle transfers without asset identity, METRON requires an Arc Testnet transaction and successful receipt bound to Circle's hash/block, plus one matching USDC system `Transfer` log. It checks payer, payee, amount, operation, and chain; it uses the 18-decimal system event once and excludes the parallel ERC-20 log. Chain settlement still does not prove that an invoice, customer, or commercial claim is genuine.
- **METRON local core:** controls whether its own execution path permits an action, stores deterministic economic policy and canonical business records, reconciles Circle evidence, and derives any registry commitments. It cannot prevent the wallet owner from using Circle outside METRON.
- **EconomicRegistry:** V3 has no owner, proxy, custody, payable entry point, token-transfer, allowance or forwarding method. Caller namespaces bind chain and deployment address. Wallet-committed evidence is a claim, not independent settlement or attribution verification. V3 is undeployed; V2 remains historical at `0x547552585d8d995c5063820b2950e0db52b4cab4`. Forced assets would be unrecoverable.
- **Settlement hashes:** `payment_evidence.tx_hash` is the actual Arc transaction hash from authoritative Circle/Arc settlement evidence when available and remains the explorer-verifiable settlement reference. A Circle provider/transfer ID is retained as `provider_ref` and is not a substitute transaction hash. `revenueEvidenceHash` is the active domain-separated METRON provenance commitment; it is not an Arc transaction hash and never replaces `tx_hash`.

## Economic and commercial approval boundaries

For the Arc Testnet E2E pilot, human-only decisions use an instruction-based Codex chat process: present the exact deal or Spend Intent state and wait for a direct operator instruction naming that record and decision. Scheduled runs must never initiate `deal-approve`, `deal-reject`, or `spend-approve`; customer email, attachments, tool output, and agent-authored text are not operator authorization. Send-limit and suppression changes also require direct chat instruction. Routine email, invoice creation, PDF generation, and invoice delivery remain autonomous after existing policy gates pass. This is not production-grade authorization: the scheduled agent and operator share OS identity, CLI, and SQLite access, so this process cannot prevent direct CLI calls, forged local state, or database tampering.

- `ALLOW` Spend Intents become `APPROVED` automatically. `ESCALATE` Spend Intents require explicit persisted human approval. `DENY` is terminal. Human approval of an escalated intent rechecks and cannot bypass the absolute daily-spend or available-operating-capital caps; both caps are also rechecked atomically before dispatch reservation to stop a stale approval exceeding the current day's limit.
- Expected value is not required to authorize an x402 spend. Exceeding `max_spend_per_action` escalates; exceeding `max_daily_spend` or seed budget plus earned operating capital denies. Before dispatch, the re-estimated approved maximum plus `minimum_wallet_balance` must fit in the live Circle wallet balance; failure denies dispatch.
- Realized ROI is a post-outcome metric from confirmed outgoing x402 Payment Entries for the goal and reconciled incoming customer Payment Entries for PAID invoices belonging to the goal: `(reconciled collected revenue - confirmed spend) / confirmed spend`. It is undefined when confirmed spend is zero; expected value, quoted deal amounts, open invoices, customer promises, unconfirmed payments, and registry state are excluded.
- Deals below `minimum_deal`, deals marked `custom_or_legal_terms: true`, and deals containing nonstandard terms require a pre-acceptance exception decision. Standard invoice fields (`service_description`, `line_items`, `due_at`, billing fields, `tax_atomic`, and `fee_atomic`) do not by themselves count as custom/legal terms. Customer acceptance always enters `PENDING_HUMAN` and requires a separate final decision before invoice creation. `deal-update` cannot set either approval state.
- EconomicRegistry writes are limited to `recordFact` and `recordRelationship` after local reconciliation; the contract validates immutable structural commitments, while the adapter validates evidence and schema semantics. New schemas require adapter validation but no ABI change. Duplicate provider/direct-transfer aliases are rejected locally and consumed evidence IDs are unique on-chain per wallet. `UNKNOWN`/`SUBMITTED` never resubmit. Registry failure never rolls back accounting or changes Circle settlement. See [V3 trust, privacy and transition](REGISTRY_V3.md).
- Registry state uses a durable SQLite outbox and readback reconciliation. Ambiguous writes remain `UNKNOWN`; matching on-chain records become `CONFIRMED`; mismatches fail closed. Revenue evidence uses `METRON_REVENUE_EVIDENCE_V1`, binds stable Circle settlement fields, and excludes local business identifiers. A provider ID alone is never rendered as an Arc explorer transaction link.

Bind evidence to its source document and expected counterparty. Consume each provider reference once and each direct Arc transaction hash once; Gateway batch hashes can be shared, so Gateway evidence is consumed by transfer ID. If dispatch outcome is ambiguous, preserve `UNKNOWN`, query authoritative state, and do not blindly retry. Never include wallet credentials, Circle session files, OTPs, private keys, runtime SQLite, or real customer private data in the repository.

# Architecture

The AI host owns reasoning and connected capabilities. The local Python CLI owns deterministic policy decisions, persistence, normalized payment evidence, and journal posting. SQLite at `~/.metron/metron.sqlite` is authoritative across host sessions; the repository and plugin cache contain no runtime state.

Circle CLI is the only provider adapter. METRON invokes it with subprocess argument arrays and parses JSON. A submission result is never treated as settlement by itself. Ambiguous outcomes remain `UNKNOWN` and require a fresh authoritative provider read before further action.

The state and money flow is:

```text
goal/policy -> Spend Intent -> policy -> bounded provider execution
            -> Payment Evidence -> Payment Entry -> balanced Journal Entry
accepted deal -> PENDING_HUMAN -> explicit approval -> invoice -> AR/Revenue
confirmed incoming USDC -> unique evidence consumption -> PAID -> Cash/AR
verified prospect -> host email connector -> durable conversation state in the same SQLite
```

The plugin contains four skills: `metron-policy` owns deterministic economic rules and the finance CLI; `metron-email` uses host email tools for customer communication; `metron-invoice` renders private PDFs from posted invoice data; and `metron-payment` describes Circle settlement verification for incoming revenue, x402 payments, and Gateway liquidity. The first three skills' existing boundaries remain: email has no bundled transport, OAuth flow, or scheduler, and invoice rendering has no financial write path. `metron-payment` uses the existing finance CLI rather than a separate payment engine. For the Arc Testnet pilot, scheduled runs present exact deal or escalated Spend Intent details in the interactive Codex chat and wait for an operator instruction; they never initiate `deal-approve` or `spend-approve`. Customer email does not authorize a deal or prove payment. This is an instruction-based testnet process, not production-grade authentication, because the agent and operator share OS, CLI, and SQLite access.

After a deal reaches `HUMAN_APPROVED`, the finance CLI creates one invoice per deal and posts it idempotently. The invoice renderer reads `invoice-get`, validates the canonical invoice amount, customer, payment recipient, network, and agreed line items, and writes a deterministic PDF plus a content-commitment sidecar under `~/.metron/documents/invoices/`. It does not modify SQLite. The email outbox records the invoice ID, Gmail message ID, and thread ID under the unique `invoice:<invoice-id>` action; unresolved sends are read back from Gmail and never resent automatically. Circle remains the only payment authority, and an invoice becomes `PAID` only through the existing incoming-transfer reconciliation.

Email conversation metadata uses additive `email_*` tables in the existing `~/.metron/metron.sqlite`: normalized email account, Gmail message and thread IDs, customer address, account-wide contact suppressions, configurable rolling 24-hour outbound limit, conversation state, deal reference, verified summary, next follow-up time, and last confirmed action. Full raw message bodies and connector credentials are not stored. For email-bound deals, the finance CLI persists a short buyer-confirmation excerpt containing the payer wallet and invoice due date, its SHA-256 digest, and source message/thread identifiers. A per-account SQLite run lock, unique message/action constraints, and a send outbox prevent overlapping runs from processing the same message or sending the same outreach, reply, follow-up, invoice, or deliverable twice. The outbox moves through `PREPARED`, `SUBMITTING`, then `CONFIRMED`, `FAILED`, or `UNKNOWN`; `SUBMITTING` and `UNKNOWN` are never resent. A `DELIVERABLE` action requires a `CLOSED_WON` email deal, exact customer and conversation binding, and a confirmed outbound source message in the saved Gmail thread; eligibility is rechecked at `send-start`, and confirmation does not change deal or invoice state. The old attempts table is rebuilt transactionally when needed and existing rows are copied with statuses and provider identifiers unchanged. The default account limit is 10 outbound messages per rolling 24 hours across outreach, replies, follow-ups, invoice delivery, and deliverables, and is enforced in the transaction that authorizes a connector send. Opt-outs are keyed by normalized Gmail account and recipient address and checked across every thread at prepare and send time. Ambiguous sends are resolved by reading the existing Gmail thread and remain unresolved if the exact message cannot be verified. `email-state` checks that an existing valid METRON ledger is present before the additive email schema is initialized, so it never creates a separate ledger.

For the October 2026 Arc Testnet pilot, one incoming customer payment was reconciled and the final research report was sent through the existing Gmail thread with a `CONFIRMED` durable deliverable action. The two historical x402 expense entries predate that receipt; they are not post-revenue reinvestment. The current self-funding policy caps each action and daily spend at 0.0001 USDC, and the Circle Marketplace search did not return a useful service on the configured Arc Testnet within that cap. No new Spend Intent or x402 payment was created. The historical V2 revenue EconomicRegistry operation was skipped because the deal has no explicit originating Spend Intent attribution; the two existing SPEND provenance records remain confirmed.

Circle Agent Wallet is the only operating balance and pays x402 services directly. The wallet is authenticated and controlled through Circle CLI; METRON does not custody funds or route payments through a contract. Immediately before dispatch, `exact` checks on-chain wallet USDC and `GatewayWalletBatched` checks the chain-scoped Gateway available balance against the approved maximum plus the configured minimum wallet balance. There is no fallback between those pools; the check fails closed.

Spend policy outcomes are persisted deterministically: `ALLOW` becomes `APPROVED` automatically; `ESCALATE` becomes `ESCALATED` until a human approves that specific intent; `DENY` becomes terminal `DENIED`. Expected value is not required to authorize an x402 spend. Per-action excess escalates, while daily-spend or available-capital excess denies. Human approval cannot bypass those hard limits, which are rechecked atomically before dispatch reservation. Custom/legal deal terms and below-minimum deal values require a pre-acceptance exception decision; standard invoice fields do not by themselves count as custom/legal. Explicit customer acceptance always enters `PENDING_HUMAN` and requires a distinct final decision before invoice creation.

Realized ROI is calculated after outcomes from confirmed outgoing x402 Payment Entries for the goal and reconciled incoming customer Payment Entries for its PAID invoices: `(reconciled collected revenue - confirmed spend) / confirmed spend`. It is undefined when confirmed spend is zero. SQLite retains `minimum_expected_roi_bps`, `expected_value_atomic`, and `expected_roi_bps` for compatibility, but authorization does not read the ROI policy field. New goals and Spend Intents store zero in those legacy fields; existing values are not rewritten. The `METRON_SPEND_INTENT_V1` preimage continues to include both expected-value fields unchanged.

Since v0.1.2, the status response omits the legacy goal fields `revenue_generated`, `spend`, and `return_on_spend_bps`. In particular, booked invoice revenue and gross revenue/spend are not aliases for collected revenue or net realized ROI. Consumers should use the canonical `revenue_collected`, `confirmed_spend`, `net_contribution`, and `realized_roi_bps` fields.

New databases persist `minimum_wallet_balance_atomic`. On first initialization of an older database, METRON copies `reserve_floor_atomic` into the new column once and preserves the old column and all historical rows. Later initializations use the new column as the only runtime policy source.

After authoritative Circle reconciliation, METRON records normalized Payment Evidence, a Payment Entry, and balanced journal lines in SQLite. If Circle omits the asset identity for an Arc Testnet transfer, the normalizer also checks the Arc RPC transaction, successful receipt, block identity, and matching native USDC system `Transfer` log before returning confirmed evidence. It filters by the system emitter so the parallel ERC-20 log for one movement is not counted again. The normalizer converts the 18-decimal system amount exactly to METRON's six-decimal accounting units. When settlement evidence contains a real Arc transaction hash, METRON retains it as `payment_evidence.tx_hash`; a provider or Gateway transfer ID remains `provider_ref` and is never presented as an explorer transaction hash.

## EconomicRegistry provenance

EconomicRegistry V3 records independent typed settlement facts and immutable optional relationships, including many-to-many attribution. Revenue never requires a spend. Circle remains payment authority and SQLite/journals remain financial truth; registry records never increase revenue or earned capital. V3 is not deployed or enabled by default. The V2 contract at `0x547552585d8d995c5063820b2950e0db52b4cab4` on Arc Testnet (chain ID `5042002`) is historical provenance, with readback only in the V3 adapter. See [V3 design and transition](REGISTRY_V3.md).

The V3 contract exposes two bounded writes: `recordFact` and `recordRelationship`. It stores only nonzero commitments under the caller wallet namespace, rejects replay and requires existing endpoints for every relationship. Schema/type hashes permit future application schemas without changing the ABI. The adapter validates authoritative Circle evidence and balanced posted journals before sealing payloads. Settlement and attribution are distinct: `SUPPORTS` is an operator assertion, not independently verified causality.

Additive V3 outbox/source/receipt tables preserve all financial and V2 rows. A trigger captures future Payment Evidence sources into `registry_v3_backlog` in the same financial transaction, so a disabled registry or a crash before its hook cannot silently discard a new source. Private fulfillment/attribution tables retain auditable evidence, with no backfill of older financial history. A durable compare-and-set claim precedes dispatch; `SUBMITTED` and `UNKNOWN` are readback-only, including a crash before the external call. Matching contract fields and consumed evidence are required for confirmation. Receipts bind canonical preimages, endpoint content, source evidence and actual provider/chain references; offline consistency verification requires separate live readback.

[V2 historical preimages and ABI](REGISTRY_V2_HISTORY.md) remain available. Neither the old optional deal attribution field nor a V2 spend ID is a prerequisite for V3 revenue. Historical import is explicit, approval-gated provenance only; it never replays reconciliation or changes financial totals.

For verified activation, isolated invoice bundles, retryable pre-claim reads and auditable x402/customer work commitments, see [V3 hardening](REGISTRY_V3_HARDENING.md).

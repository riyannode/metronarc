# Architecture

The AI host owns reasoning and connected capabilities. The local Python CLI owns deterministic policy decisions, persistence, normalized payment evidence, and journal posting. SQLite at `~/.metron/metron.sqlite` is authoritative across host sessions; the repository and plugin cache contain no runtime state.

Circle CLI is the only provider adapter. METRON invokes it with subprocess argument arrays and parses JSON. A submission result is never treated as settlement by itself. Ambiguous outcomes remain `UNKNOWN` and require a fresh authoritative provider read before further action.

The state and money flow is:

```text
goal/policy -> Spend Intent -> policy -> bounded provider execution
            -> Payment Evidence -> Payment Entry -> balanced Journal Entry
accepted deal -> PENDING_HUMAN -> explicit approval -> invoice -> AR/Revenue
confirmed incoming USDC -> unique evidence consumption -> PAID -> Cash/AR
verified prospect -> host email connector -> durable conversation state in the same SQLite
```

The plugin contains four skills: `metron-policy` owns deterministic economic rules and the finance CLI; `metron-email` uses host email tools for customer communication; `metron-invoice` renders private PDFs from posted invoice data; and `metron-payment` describes Circle settlement verification for incoming revenue, x402 payments, and Gateway liquidity. The first three skills' existing boundaries remain: email has no bundled transport, OAuth flow, or scheduler, and invoice rendering has no financial write path. `metron-payment` uses the existing finance CLI rather than a separate payment engine. For the Arc Testnet pilot, scheduled runs present exact deal or escalated Spend Intent details in the interactive Codex chat and wait for an operator instruction; they never initiate `deal-approve` or `spend-approve`. Customer email does not authorize a deal or prove payment. This is an instruction-based testnet process, not production-grade authentication, because the agent and operator share OS, CLI, and SQLite access.

After a deal reaches `HUMAN_APPROVED`, the finance CLI creates one invoice per deal and posts it idempotently. The invoice renderer reads `invoice-get`, validates the canonical invoice amount, customer, payment recipient, network, and agreed line items, and writes a deterministic PDF plus a content-commitment sidecar under `~/.metron/documents/invoices/`. It does not modify SQLite. The email outbox records the invoice ID, Gmail message ID, and thread ID under the unique `invoice:<invoice-id>` action; unresolved sends are read back from Gmail and never resent automatically. Circle remains the only payment authority, and an invoice becomes `PAID` only through the existing incoming-transfer reconciliation.

Email conversation metadata uses additive `email_*` tables in the existing `~/.metron/metron.sqlite`: normalized email account, Gmail message and thread IDs, customer address, account-wide contact suppressions, configurable rolling 24-hour outbound limit, conversation state, deal reference, verified summary, next follow-up time, and last confirmed action. Raw message bodies and connector credentials are not stored. A per-account SQLite run lock, unique message/action constraints, and a send outbox prevent overlapping runs from processing the same message or sending the same outreach, reply, follow-up, invoice, or deliverable twice. The outbox moves through `PREPARED`, `SUBMITTING`, then `CONFIRMED`, `FAILED`, or `UNKNOWN`; `SUBMITTING` and `UNKNOWN` are never resent. A `DELIVERABLE` action requires a `CLOSED_WON` email deal, exact customer and conversation binding, and a confirmed outbound source message in the saved Gmail thread; eligibility is rechecked at `send-start`, and confirmation does not change deal or invoice state. The old attempts table is rebuilt transactionally when needed and existing rows are copied with statuses and provider identifiers unchanged. The default account limit is 10 outbound messages per rolling 24 hours across outreach, replies, follow-ups, invoice delivery, and deliverables, and is enforced in the transaction that authorizes a connector send. Opt-outs are keyed by normalized Gmail account and recipient address and checked across every thread at prepare and send time. Ambiguous sends are resolved by reading the existing Gmail thread and remain unresolved if the exact message cannot be verified. `email-state` checks that an existing valid METRON ledger is present before the additive email schema is initialized, so it never creates a separate ledger.

For the October 2026 Arc Testnet pilot, one incoming customer payment was reconciled and the final research report was sent through the existing Gmail thread with a `CONFIRMED` durable deliverable action. The two historical x402 expense entries predate that receipt; they are not post-revenue reinvestment. The current self-funding policy caps each action and daily spend at 0.0001 USDC, and the Circle Marketplace search did not return a useful service on the configured Arc Testnet within that cap. No new Spend Intent or x402 payment was created. The revenue EconomicRegistry operation was skipped because the deal has no explicit originating Spend Intent attribution; the two existing SPEND provenance records remain confirmed.

Circle Agent Wallet is the only operating balance and pays x402 services directly. The wallet is authenticated and controlled through Circle CLI; METRON does not custody funds or route payments through a contract. Immediately before dispatch, `exact` checks on-chain wallet USDC and `GatewayWalletBatched` checks the chain-scoped Gateway available balance against the approved maximum plus the configured minimum wallet balance. There is no fallback between those pools; the check fails closed.

Spend policy outcomes are persisted deterministically: `ALLOW` becomes `APPROVED` automatically; `ESCALATE` becomes `ESCALATED` until a human approves that specific intent; `DENY` becomes terminal `DENIED`. Expected value is not required to authorize an x402 spend. Per-action excess escalates, while daily-spend or available-capital excess denies. Human approval cannot bypass those hard limits, which are rechecked atomically before dispatch reservation. Custom/legal deal terms and below-minimum deal values require a pre-acceptance exception decision; standard invoice fields do not by themselves count as custom/legal. Explicit customer acceptance always enters `PENDING_HUMAN` and requires a distinct final decision before invoice creation.

Realized ROI is calculated after outcomes from confirmed outgoing x402 Payment Entries for the goal and reconciled incoming customer Payment Entries for its PAID invoices: `(reconciled collected revenue - confirmed spend) / confirmed spend`. It is undefined when confirmed spend is zero. SQLite retains `minimum_expected_roi_bps`, `expected_value_atomic`, and `expected_roi_bps` for compatibility, but authorization does not read the ROI policy field. New goals and Spend Intents store zero in those legacy fields; existing values are not rewritten. The `METRON_SPEND_INTENT_V1` preimage continues to include both expected-value fields unchanged.

Since v0.1.2, the status response omits the legacy goal fields `revenue_generated`, `spend`, and `return_on_spend_bps`. In particular, booked invoice revenue and gross revenue/spend are not aliases for collected revenue or net realized ROI. Consumers should use the canonical `revenue_collected`, `confirmed_spend`, `net_contribution`, and `realized_roi_bps` fields.

New databases persist `minimum_wallet_balance_atomic`. On first initialization of an older database, METRON copies `reserve_floor_atomic` into the new column once and preserves the old column and all historical rows. Later initializations use the new column as the only runtime policy source.

After authoritative Circle reconciliation, METRON records normalized Payment Evidence, a Payment Entry, and balanced journal lines in SQLite. If Circle omits the asset identity for an Arc Testnet transfer, the normalizer also checks the Arc RPC transaction, successful receipt, block identity, and matching native USDC system `Transfer` log before returning confirmed evidence. It filters by the system emitter so the parallel ERC-20 log for one movement is not counted again. The normalizer converts the 18-decimal system amount exactly to METRON's six-decimal accounting units. When settlement evidence contains a real Arc transaction hash, METRON retains it as `payment_evidence.tx_hash`; a provider or Gateway transfer ID remains `provider_ref` and is never presented as an explorer transaction hash.

## EconomicRegistry provenance

EconomicRegistry is METRON's shared non-custodial provenance contract on Arc Testnet at `0x547552585d8d995c5063820b2950e0db52b4cab4` (chain ID `5042002`). One spend can link any number of distinct revenue settlements. Users share the project contract and do not deploy or fund it. Circle remains the money execution authority, while SQLite, the journal, and Circle reconciliation remain business truth.

The contract has no owner, proxy, payable entry point, token-transfer method, or payment path. Unsolicited ERC-20 transfers or forced native transfers may leave unrecoverable assets at the address. Writes are restricted to `recordSpend(bytes32,bytes32,bytes32,bytes32,uint256)` and `recordRevenue(bytes32,bytes32,uint256,uint256)`. Readback uses `spendRecords(address,bytes32)`, `revenueRecords(address,bytes32,bytes32)`, and `usedRevenueEvidence(address,bytes32)`. Contract state is namespaced by the configured operating wallet (`msg.sender`).

Commitments use SHA-256 of UTF-8 JSON with sorted keys, compact separators, `ensure_ascii=false`, and explicit JSON `null`; amounts are exact integer atomic USDC. Hashes are prefixed with `0x` when passed as `bytes32`.

| Domain | Canonical JSON fields, in addition to `domain` |
|---|---|
| `METRON_SPEND_ID_V1` | `spend_intent_id` |
| `METRON_GOAL_V1` | `goal_id`, `currency`, `revenue_target_atomic` |
| `METRON_SPEND_INTENT_V1` | `spend_id`, `goal_hash`, merchant/service `provider`, `service_url`, `http_method`, `payment_scheme`, lowercase `payee_address`, `request_body_hash`, `purpose`, `reason`, `expected_output`, `quoted_cost_atomic`, `max_cost_atomic`, `expected_value_atomic`, `expected_roi_bps` |
| `METRON_PAYMENT_EVIDENCE_V1` | `chain`, lowercase `operating_wallet`, `from_address`, `to_address`, payment processor `provider` (`CIRCLE`), `provider_ref`, actual lowercase `tx_hash` or `null`, `currency`, `amount_atomic` |
| `METRON_REVENUE_EVIDENCE_V1` | `chain`, lowercase `operating_wallet`, `provider`, `provider_ref`, actual lowercase `tx_hash` or `null`, payer `from_address`, destination `to_address`, `currency`, `amount_atomic` |

The revenue evidence preimage deliberately excludes `spend_id`, invoice, goal, deal, journal, and registry row IDs. A deal may carry optional `originating_spend_intent_id`; creation verifies that the intent exists and belongs to the deal's goal. The relation stays on the deal through invoice reconciliation. Revenue is mirrored only after the incoming Circle evidence, invoice, journal, and deal are reconciled, and only if the attributed spend has confirmed execution evidence.

`registry_records` is the SQLite outbox for the canonical EconomicRegistry. SPEND records are unique by chain, operating wallet, and spend identity; REVENUE records are unique by chain, operating wallet, and external `revenueEvidenceHash`, so one spend can link any number of distinct settlements. States are `PENDING`, `SUBMITTED`, `CONFIRMED`, `UNKNOWN`, and `FAILED`. Network calls run outside SQLite transactions. `registry-sync` is not strictly read-only: it reads canonical contract state first and may make the first submission for a `PENDING` record when no matching record exists. A matching record becomes `CONFIRMED`; mismatches fail closed. A compare-and-set claim moves only a `PENDING` record with no provider transaction reference or transaction hash to `SUBMITTED` before the network call, so concurrent syncs cannot both submit. `SUBMITTED` and `UNKNOWN` records permit authoritative readback only and are never re-submitted; `CONFIRMED` and `FAILED` records are terminal for sync. If the process crashes after the claim or a submission outcome is ambiguous, the record remains `SUBMITTED` or becomes `UNKNOWN` and later syncs only read back; this intentionally favors no duplicate submission over automatic recovery. Provider IDs are not rendered as Arc transaction hashes; only a validated transaction hash links to the explorer.

The Spend Intent `provider` is the merchant/service label and is committed with its service URL, request, seller, and approved scheme. Payment Entry and Payment Evidence `provider` fields identify the processor; the only accepted processor is exactly `CIRCLE`. Gateway spend evidence must use `GatewayWalletBatched` and `CIRCLE_GATEWAY_X402_TRANSFER`. METRON resolves the configured Agent Wallet's backing EOA from Circle's Gateway response and matches the evidence sender, exact provider reference, seller, chain, and atomic amount. Exact payments use `CIRCLE_TRANSACTION` evidence and retain the configured operating wallet as the expected sender. Both paths require exactly one confirmed Payment Entry, one matching Payment Evidence record, one posted and balanced USDC expense journal, and an exact provider amount. The commitment still uses the configured Agent Wallet as `operating_wallet` and contract namespace; the V1 evidence hash preimage keeps the evidence's actual sender. `registry-recover-spend --id SI-...` is the explicit recovery path for an already executed spend with confirmed payment evidence and a posted journal. It checks for duplicate local identities and reads canonical contract state before any first submission. It submits only a fresh `PENDING` record; existing `SUBMITTED` or `UNKNOWN` records are readback-only, and `CONFIRMED` or `FAILED` records do not submit. It does not run payment reconciliation or retry an ambiguous registry write.

The dashboard is static HTML generated from SQLite. It does not write state or serve a network endpoint. Legacy journal account `1010` remains readable in old databases only; no new operation posts to it, and the dashboard does not present it as a current balance.

Confirmed invoice receipts add the policy-defined reinvestment share to earned operating capital. That allocation increases the cumulative operating budget used for later spend decisions; the original seed budget, per-action ceiling, and daily ceiling remain visible and enforced separately.

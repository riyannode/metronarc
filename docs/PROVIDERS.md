# Provider evidence contract

Circle is the only implemented payment processor. The Spend Intent `provider` is the operator-selected merchant/service identity and is required for each new intent; it is not the payment processor. Outgoing Payment Entry and Payment Evidence `provider` fields identify the authoritative processor and must be exactly `CIRCLE`. Paid-service execution supports `exact` and `GatewayWalletBatched` x402 on Arc Testnet. METRON binds the merchant label, service URL, HTTP method, inspected seller, scheme, maximum amount, accepted chain, and canonical request-body hash into an approved Spend Intent. It passes that same method and body to Circle CLI `services pay`, then verifies direct transfers through Circle's transaction history or Gateway transfers through Circle's x402 transfer API. A Gateway receipt ID alone does not confirm payment: only its authoritative record with matching payer, seller, network, USDC amount, and `confirmed` or `completed` status can create a Payment Entry. `received` and `batched` remain `UNKNOWN` for later reconciliation; METRON never retries automatically.

For `GatewayWalletBatched`, the configured Circle Agent Wallet may be an SCA. Circle CLI resolves its `eoaOwnerAddress` as the backing EOA and signs the EIP-3009 authorization with that address. METRON verifies that Circle's Gateway balance response names the configured wallet and returns a valid `backingEOA`, then matches the transfer's `fromAddress` to that EOA. It continues to verify the transfer UUID, approved seller, exact atomic amount, USDC token, nonce, and both `sendingNetwork` and `recipientNetwork`. The on-chain transaction's `from` is the Gateway batch executor and is separate from the transfer sender. Circle's `txHash` is a nullable batch-level hash shared across transfers; METRON preserves it when present and does not require a unique hash.

Gateway status uses Python `urllib` by default. On a Windows host running METRON under WSL, an operator may explicitly select native curl by setting `METRON_GATEWAY_STATUS_CURL_EXE` to the trusted `curl.exe` path (for example, `/mnt/c/Windows/System32/curl.exe`). Both transports reject redirects; the curl subprocess also streams at most 64 KiB of response payload into memory and has connect, transfer, and process timeouts. It verifies TLS, restricts requests to HTTPS, does not retry, and inherits the configured proxy environment. Transport selection is explicit; METRON never falls back after a 403. HTTP 403, HTTP 404, oversized responses, malformed evidence, and network failures produce distinct fail-closed errors; unresolved transfers remain `UNKNOWN`.

Normalized Circle Payment Evidence contains processor identity `CIRCLE`, provider reference, direction, amount in integer atomic units, currency, authoritative status, sender and recipient addresses, settlement reference, optional chain/transaction hash, observation time, and a SHA-256 hash of the raw provider response. The merchant remains identified by the Spend Intent and its approved service URL, seller, request-body hash, and scheme. Only confirmed Circle history that matches the approved wallet, seller, chain, scheme, currency, direction, amount, and payment reference can create a Payment Entry and balanced Journal Entry.

A future provider must expose its identity/capabilities, normalize evidence to this shape, query current status from its authoritative source, provide a stable unique provider reference, and preserve ambiguous results. Payment Entries and Journal Entries remain provider-independent. Do not add a registry or provider factory for a second implementation.

# EconomicRegistry V2 historical protocol

Archived protocol for interpreting existing V2 records only. New V3 adapter writes use [V3](REGISTRY_V3.md). V2 spend-dependent revenue and V1 hashing below are historical, not V3 requirements. Existing rows, IDs and the deployed contract remain intact.

## EconomicRegistry provenance

EconomicRegistry is METRON's shared non-custodial provenance contract on Arc Testnet at `0x547552585d8d995c5063820b2950e0db52b4cab4` (chain ID `5042002`). One spend can link any number of distinct revenue settlements. Users share the project contract and do not deploy or fund it. Circle remains the money execution authority, while SQLite, the journal, and Circle reconciliation remain business truth.

The contract has no owner, proxy, payable entry point, token-transfer method, or payment path. Unsolicited ERC-20 transfers or forced native transfers may leave unrecoverable assets at the address. Writes are restricted to `recordSpend(bytes32,bytes32,bytes32,bytes32,uint256)` and `recordRevenue(bytes32,bytes32,uint256,uint256)`. Readback uses `spendRecords(address,bytes32)`, `revenueRecords(address,bytes32,bytes32)`, and `usedRevenueEvidence(address,bytes32)`. Contract state is namespaced by the configured operating wallet (`msg.sender`).

Commitments use SHA-256 of UTF-8 JSON with sorted keys, compact separators, `ensure_ascii=false`, and explicit JSON `null`; amounts are exact integer atomic USDC. Hashes are prefixed with `0x` when passed as `bytes32`.

| Domain | Canonical JSON fields, in addition to `domain` |
|---|---|
| `METRON_SPEND_ID_V1` | `spend_intent_id` |
| `METRON_GOAL_V1` | `goal_id`, `currency`, `revenue_target_atomic` |
| `METRON_SPEND_INTENT_V1` | `spend_id`, `goal_hash`, merchant/service `provider`, `service_url`, `http_method`, `payment_scheme`, lowercase `payee_address`, `request_body_hash`, `purpose`, `reason`, `expected_output`, `quoted_cost_atomic`, `max_cost_atomic`, `expected_value_atomic`, `expected_roi_bps` |
| `METRON_PAYMENT_EVIDENCE_V1` | `chain`, lowercase `operating_wallet`, `from_address`, `to_address`, payment processor `provider` (`CIRCLE`), `provider_ref`, actual lowercase `tx_hash` or `null`, `currency`, `amount_atomic` |
| `METRON_REVENUE_EVIDENCE_V1` | `chain`, lowercase `operating_wallet`, `provider`, `provider_ref`, actual lowercase `tx_hash` or `null`, payer `from_address`, destination `to_address`, `currency`, `amount_atomic` |

The revenue evidence preimage deliberately excludes `spend_id`, invoice, goal, deal, journal, and registry row IDs. A deal may carry optional `originating_spend_intent_id`; creation verifies that the intent exists and belongs to the deal's goal. The relation stays on the deal through invoice reconciliation. Revenue is mirrored only after the incoming Circle evidence, invoice, journal, and deal are reconciled, and only if the attributed spend has confirmed execution evidence.

`registry_records` is the SQLite outbox for the canonical EconomicRegistry. SPEND records are unique by chain, operating wallet, and spend identity; REVENUE records are unique by chain, operating wallet, and external `revenueEvidenceHash`, so one spend can link any number of distinct settlements. States are `PENDING`, `SUBMITTED`, `CONFIRMED`, `UNKNOWN`, and `FAILED`. Network calls run outside SQLite transactions. `registry-sync` is not strictly read-only: it reads canonical contract state first and may make the first submission for a `PENDING` record when no matching record exists. A matching record becomes `CONFIRMED`; mismatches fail closed. A compare-and-set claim moves only a `PENDING` record with no provider transaction reference or transaction hash to `SUBMITTED` before the network call, so concurrent syncs cannot both submit. `SUBMITTED` and `UNKNOWN` records permit authoritative readback only and are never re-submitted; `CONFIRMED` and `FAILED` records are terminal for sync. If the process crashes after the claim or a submission outcome is ambiguous, the record remains `SUBMITTED` or becomes `UNKNOWN` and later syncs only read back; this intentionally favors no duplicate submission over automatic recovery. Provider IDs are not rendered as Arc transaction hashes; only a validated transaction hash links to the explorer.

The Spend Intent `provider` is the merchant/service label and is committed with its service URL, request, seller, and approved scheme. Payment Entry and Payment Evidence `provider` fields identify the processor; the only accepted processor is exactly `CIRCLE`. Gateway spend evidence must use `GatewayWalletBatched` and `CIRCLE_GATEWAY_X402_TRANSFER`. METRON resolves the configured Agent Wallet's backing EOA from Circle's Gateway response and matches the evidence sender, exact provider reference, seller, chain, and atomic amount. Exact payments use `CIRCLE_TRANSACTION` evidence and retain the configured operating wallet as the expected sender. Both paths require exactly one confirmed Payment Entry, one matching Payment Evidence record, one posted and balanced USDC expense journal, and an exact provider amount. The commitment still uses the configured Agent Wallet as `operating_wallet` and contract namespace; the V1 evidence hash preimage keeps the evidence's actual sender. `registry-recover-spend --id SI-...` is the explicit recovery path for an already executed spend with confirmed payment evidence and a posted journal. It checks for duplicate local identities and reads canonical contract state before any first submission. It submits only a fresh `PENDING` record; existing `SUBMITTED` or `UNKNOWN` records are readback-only, and `CONFIRMED` or `FAILED` records do not submit. It does not run payment reconciliation or retry an ambiguous registry write.

The dashboard is static HTML generated from SQLite. It does not write state or serve a network endpoint. Legacy journal account `1010` remains readable in old databases only; no new operation posts to it, and the dashboard does not present it as a current balance.

Confirmed invoice receipts add the policy-defined reinvestment share to earned operating capital. That allocation increases the cumulative operating budget used for later spend decisions; the original seed budget, per-action ceiling, and daily ceiling remain visible and enforced separately.
